# Online Bar Setup Guide

Use this guide to configure the Supabase database and the external services used by the application.

## Supabase setup

1. Open your [Supabase SQL Editor](https://supabase.com/dashboard/project/_/sql/new).
2. Copy [`supabase/FINAL_ESTABLISHMENT_SQL.sql`](./supabase/FINAL_ESTABLISHMENT_SQL.sql).
3. Paste and run the script to create the application tables and views.

For an already-installed Onbar database that needs the accumulated feature migrations in one paste, use [`supabase/ONBAR_EXISTING_PROJECT_ALL_IN_ONE.sql`](./supabase/ONBAR_EXISTING_PROJECT_ALL_IN_ONE.sql). It combines the additive operational, CRM/consent, security, analytics, merchant/dispatch, delivery, and Buzz migrations in one transaction. Do not run it on a blank project: install the core schema above first. A failure rolls the bundle back as a unit; copy the complete error from the SQL Editor before retrying. If the existing database already has these migrations and only reports a NULL `customer_aggregate_metrics.user_id`, run [`supabase/CUSTOMER_AGGREGATE_NULL_USER_FIX.sql`](./supabase/CUSTOMER_AGGREGATE_NULL_USER_FIX.sql) by itself.

## Drink-order payment provider

The Admin → Settings → Integrations screen controls the provider for new drink-delivery online orders. Ticket payment settings are separate and are not affected by this switch. For an existing database, apply the core schema, then the updated `supabase/MERCHANT_OPERATIONS_MIGRATION.sql` and `supabase/DISPATCH_MIGRATION.sql`, followed by `supabase/PAYHERO_DRINK_ORDERS_MIGRATION.sql`. Apply the updated `supabase/RIDER_DOORSTEP_PAYMENT_MIGRATION.sql` as well so pre-paid PayHero orders cannot be treated as doorstep-collection orders. If using the all-in-one existing-project SQL, run the updated bundle and then the PayHero drink-orders migration. Configure `PAYHERO_AUTH_TOKEN`, `PAYHERO_CHANNEL_ID`, and `NEXT_PUBLIC_BASE_URL` (the deployed app's public origin) as private Vercel environment variables and redeploy before selecting PayHero. Set `PAYHERO_AUTH_TOKEN` to the Basic Auth token from PayHero (including its `Basic ` prefix); set `PAYHERO_CHANNEL_ID` to the payment channel ID, not the Account ID. Rotate credentials exposed in screenshots or messages before configuring them. Do not use a Resend API key as PayHero credentials; they are different services. Keep Paystack's server and public keys configured if you need to switch back. A PayHero payment is only marked paid after callback authentication and server-side transaction verification; test with a real low-value payment before enabling it for customers.

Configure `NEXT_PUBLIC_SUPABASE_URL` and either `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` or the legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` in the deployment environment. Both variables must contain Supabase project values; a Supabase `sb_publishable_...` key is valid and is not a Stripe key. Never put a Supabase `service_role` key in a `NEXT_PUBLIC_` variable or expose it to the browser. Restart the development server after changing local environment variables.

For local development, copy `.env.example` to `.env.local` and replace the placeholders with the Project URL, anon/publishable key, and legacy `service_role` key from Supabase **Project Settings → API Keys**. Keep `SUPABASE_SERVICE_ROLE_KEY` server-only. Set the same variables in the hosting provider's private environment settings and redeploy; changing SQL alone cannot connect a deployed app to a Supabase project.

For the Admin **Bite Command**, **Kitchen**, **Customers**, and **Dispatch** screens, configure the server-only `SUPABASE_SERVICE_ROLE_KEY` and run [`supabase/ADMIN_KITCHEN_CONNECTION_MIGRATION.sql`](./supabase/ADMIN_KITCHEN_CONNECTION_MIGRATION.sql) in the SQL Editor after the core schema. These screens use authenticated server APIs for protected order, profile, and product data; do not add public read/write policies for private customer orders. The script adds missing food/order columns and indexes and finishes with a small connection check. Do not paste the service-role key into browser code or a `NEXT_PUBLIC_` variable.

For an existing database, run the `ALTER TABLE public.orders` migration block in the script's **Operations & Logistics** section to add gift-card details to existing orders. Do not re-run the entire setup script on a live database just to apply that migration.

For the private Admin → **Task Control** board, run [`supabase/ADMIN_TASKS_MIGRATION.sql`](./supabase/ADMIN_TASKS_MIGRATION.sql) after the core schema and configure the server-only `SUPABASE_SERVICE_ROLE_KEY`. It creates the protected task table and seeds four uncompleted setup/pilot tasks with links to messaging, affiliate, gate-staff, and ticketing operations. The board displays a setup error until this migration has been applied; it does not mark any setup or test as completed automatically.

For the current delivery, audience, and analytics features on an already configured database, run [`supabase/OPERATIONAL_FEATURES_MIGRATION.sql`](./supabase/OPERATIONAL_FEATURES_MIGRATION.sql) in the SQL Editor. It adds the souvenir fields and reporting functions used by the admin screens without re-running the full setup script. It also creates the notification templates, private per-customer notification inbox/log, and Realtime publication entries used by the popup manager and in-app alerts. Campaign-channel foreign keys are created to match the existing campaign ID type; if an older channel table has rows with a different ID type, missing campaign links, or references to missing campaigns, the migration stops rather than discarding or guessing at those links.

For an existing database where product-page food pairings are missing or cannot be saved from Admin, run [`supabase/PRODUCT_PAIRING_SUGGESTIONS_MIGRATION.sql`](./supabase/PRODUCT_PAIRING_SUGGESTIONS_MIGRATION.sql) in the SQL Editor. The Admin product editor writes these suggestions to `products.pairing_suggestions`, and the customer-facing product page reads the same field.

For the Governance Center on an existing database, also run [`supabase/GOVERNANCE_MIGRATION.sql`](./supabase/GOVERNANCE_MIGRATION.sql). This installs the consent and data-quality tables and repairs the consent record ID on older schemas. Consent rows are protected with row-level security, and integrity alerts are only readable through the authenticated admin server endpoint.

For the admin lockdown switch and Smart Autopilot rule registry on an existing database, run [`supabase/ADMIN_CONTROLS_MIGRATION.sql`](./supabase/ADMIN_CONTROLS_MIGRATION.sql). The migration creates the shared `settings` table if it is missing and adds missing rule columns to older installations, including `content_source`. The lockdown endpoint and autopilot editor require `SUPABASE_SERVICE_ROLE_KEY` configured on the server; it must never use a `NEXT_PUBLIC_` variable. Autopilot slots create content drafts only and do not publish to social platforms.

After the core schema is installed by [`supabase/FINAL_ESTABLISHMENT_SQL.sql`](./supabase/FINAL_ESTABLISHMENT_SQL.sql), run [`supabase/AUTH_SECURITY_MIGRATION.sql`](./supabase/AUTH_SECURITY_MIGRATION.sql) for server-side authentication attempts, brute-force alerts, blocked origins, and protected audit records. The migration creates the `staff` and `audit_logs` tables if they are missing and adds missing columns to an existing `ip_blacklist` table. Set `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_PASSWORD`, and preferably a separate high-entropy `ADMIN_SESSION_SECRET` only in the server environment. The key must not be prefixed with `NEXT_PUBLIC_`. Authentication and audit APIs return an explicit setup error until the migration and server key are in place.

For searchable order investigations and tamper-evident staff activity, run [`supabase/FORENSICS_MIGRATION.sql`](./supabase/FORENSICS_MIGRATION.sql) after both `AUTH_SECURITY_MIGRATION.sql` and [`DELIVERY_ENGINE_AND_BUZZ_MIGRATION.sql`](./supabase/DELIVERY_ENGINE_AND_BUZZ_MIGRATION.sql). It anchors existing audit and delivery history, records new orders and order-status transitions in the same hash-chained trail, and makes delivery events append-only; the chain can be verified from the Admin Audit page. This establishes integrity from the time the migration is run and cannot prove that older records were never changed beforehand. The admin Audit page can search staff, actions, and order IDs, show before/after states, and calculate elapsed time between order events. Do not purge or manually edit forensic records.

For the Admin → **Launch Readiness** workboard and consent-gated storefront search-demand report, run [`supabase/LAUNCH_READINESS_MIGRATION.sql`](./supabase/LAUNCH_READINESS_MIGRATION.sql) after the core schema. It seeds launch tasks with candid source-review statuses; an administrator must update each status and record real evidence before treating it as verified. Search insights aggregate opted-in search events and exclude email-like and phone-number-like phrases. They remain empty until visitors grant analytics consent and use storefront search. The board's system checks only confirm server configuration or basic database/schema access; they do not certify external providers, legal compliance, migration correctness, or a successful business launch.

For customer-data row-level security, server-only financial/rider data, hashed rider PINs and throttled rider sign-in, and atomic server-side loyalty awards, run [`supabase/SECURITY_HARDENING_MIGRATION.sql`](./supabase/SECURITY_HARDENING_MIGRATION.sql) after the core, dispatch, and operational schemas. It requires the `reviews` table and uses the server-only `SUPABASE_SERVICE_ROLE_KEY` for privileged operations. It intentionally removes direct browser access to order creation and status updates, financial ledger, rider records, and member reward tables; those operations must go through authenticated server APIs. The guest and signed-in checkout flows and customer guest tracking still access protected data and must be migrated before applying this migration to production. Run it on staging first, then verify checkout, customer order history/tracking, reviews, and all admin workflows.

For production admin login on Render, open the `onlinebar` web service, go to **Environment**, and set `ADMIN_PASSWORD` to the owner PIN and `ADMIN_SESSION_SECRET` to a separate high-entropy random secret. Also configure `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` for server-side authentication checks. Save the environment changes and redeploy the service. Keep all secret values in Render's private environment settings; do not commit them or add a `NEXT_PUBLIC_` prefix to secrets.

For customer-visible storefront announcements and private replies to support messages, run [`supabase/CUSTOMER_MESSAGING_MIGRATION.sql`](./supabase/CUSTOMER_MESSAGING_MIGRATION.sql). This adds the announcement table and a hashed access token for guest support threads. Admin broadcasts published in the In-App channel appear on customer storefronts; support replies are available in the customer support bubble on the submitting device, and on other devices when the customer is signed in.

Transactional order emails can be branded in Admin → Communications → Automation. For each order status, edit the email headline, button label, and accent color; preview the responsive layout, save the automation, and send a test to an address you control. The preview, test email, and live customer notification share one renderer. These fields are stored alongside the existing `customer_messaging` setting, so no additional database migration is needed. A verified transactional email sender (`JMSURF_MAIL_KEY`/`JMSURF_FROM_EMAIL` or `RESEND_API_KEY`/`RESEND_FROM_EMAIL`) is still required.

Public Contact form submissions are saved as support tickets and appear in the Admin/Lord Support workspace. The server also emails a new-ticket alert to `ADMIN_EMAIL`, falling back to the published contact email in Admin settings. Configure `RESEND_API_KEY` and a verified `RESEND_FROM_EMAIL`; the form reports when a ticket is saved but its email alert could not be sent. Contact submission throttling uses `allow_rider_login_attempt` from [`supabase/SECURITY_HARDENING_MIGRATION.sql`](./supabase/SECURITY_HARDENING_MIGRATION.sql), so apply that migration before enabling the public form on production.

For Customer CRM consent preferences and consent-aware campaigns, run [`supabase/CRM_CONSENT_MESSAGING_MIGRATION.sql`](./supabase/CRM_CONSENT_MESSAGING_MIGRATION.sql) once after the core setup and `OPERATIONAL_FEATURES_MIGRATION.sql`. Customers control promotional in-app notifications from their profile. Segment estimates and in-app broadcasts include only authenticated customers who have explicitly enabled those notifications, and campaign sends are logged. Email remains a separate explicit newsletter opt-in, with unsubscribe links and preferences retained in the subscriber table. For actual email delivery, configure `RESEND_API_KEY` and a verified sender address in `RESEND_FROM_EMAIL` on the server. SMS delivery and automated/scheduled campaigns are not configured by this migration.

For the Admin/Lord customer-management workspace, run [`supabase/CUSTOMER_CRM_MIGRATION.sql`](./supabase/CUSTOMER_CRM_MIGRATION.sql) after `FINAL_ESTABLISHMENT_SQL.sql`. It adds private staff-only customer tags, internal notes, follow-up tasks, and CRM activity history. The customer detail pages also provide contact editing and a combined order/activity timeline; the directory supports customer segments and CSV export. CRM data is accessible only through server routes restricted to owner/admin sessions. Configure `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` on the server, then deploy the application. This migration does not send customer messages.

For automated transactional messages after an order is paid, dispatched, picked up, out for delivery, or delivered, run [`supabase/CUSTOMER_NOTIFICATION_AUTOMATION_MIGRATION.sql`](./supabase/CUSTOMER_NOTIFICATION_AUTOMATION_MIGRATION.sql) after the core setup, and re-run it on existing projects to update the notification-status constraint. Configure provider credentials on the server (`RESEND_API_KEY`/`RESEND_FROM_EMAIL`, `WHATSAPP_TOKEN`/`WHATSAPP_PHONE_ID`, and/or `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_PHONE_NUMBER`), then use **Admin → Patrons → Message Automation** to edit the status templates, choose defaults, and set channels per customer. Email is the default until changed. Configure `INTERNAL_API_SECRET` on the server so verified rider status changes can invoke the notification service; it should be a separate high-entropy secret. Meta may require approved WhatsApp templates for business-initiated messages outside its customer-service window, and each provider may require a verified sender/number and customer consent.

For customer delivery push alerts, first run [`supabase/CUSTOMER_WEB_PUSH_MIGRATION.sql`](./supabase/CUSTOMER_WEB_PUSH_MIGRATION.sql) after `CUSTOMER_NOTIFICATION_AUTOMATION_MIGRATION.sql`. Generate a matching VAPID pair with `npx web-push generate-vapid-keys`, then add `WEB_PUSH_VAPID_PUBLIC_KEY`, `WEB_PUSH_VAPID_PRIVATE_KEY`, and `WEB_PUSH_SUBJECT` (for example, `mailto:ops@your-domain.example`) as private environment variables in Vercel for the Production environment. Never expose the private key in a `NEXT_PUBLIC_` variable or commit it. Redeploy after setting the variables. Verify `https://www.apexmarket.co.ke/api/push/config` reports `"configured":true`, then sign in to a customer account on a supported HTTPS browser and enable alerts in the profile. The customer must grant browser notification permission; push alerts cannot be enabled while signed out or before the database migration and server configuration are complete.

For the invite-only affiliate program, first run [`supabase/AFFILIATE_PROGRAM_MIGRATION.sql`](./supabase/AFFILIATE_PROGRAM_MIGRATION.sql), then run [`supabase/AFFILIATE_INVITATIONS_MIGRATION.sql`](./supabase/AFFILIATE_INVITATIONS_MIGRATION.sql). The first migration installs affiliate records, private read policies, agreement version/acceptance tracking, and an atomic payout request function; the second adds expiring, single-use invitations and atomic invitation acceptance. Only an authorized admin can create and revoke invitations. Invitees must sign in with the verified email address the invitation was sent to; affiliate products, referrals, earnings, and payouts remain unavailable until acceptance. Affiliate dashboards and decisions use authenticated server APIs. The agreement at `/affiliate/agreement` is explicitly marked as a draft because ONBAR legal details and several programme terms remain TO BE CONFIRMED. Finalize and legally review these terms before activating partners. The existing program defaults are 5% commission and a KSh 1,000 minimum payout. Payout requests are reviewed and paid manually by an authorized admin.

For server-backed loyalty balances, order awards, review rewards, redemptions, daily rewards, achievements, and verified purchase/referral/review missions, run [`supabase/LOYALTY_POINTS_MIGRATION.sql`](./supabase/LOYALTY_POINTS_MIGRATION.sql) after the core schema, then run [`supabase/LOYALTY_ORDER_RESERVATION_MIGRATION.sql`](./supabase/LOYALTY_ORDER_RESERVATION_MIGRATION.sql). Checkout reserves redeemed points atomically before returning an order for payment, preventing the same balance from discounting concurrent orders. Cancelled or refunded orders release the reservation once; a payment-failed order retains its points until it is cancelled or refunded so a late verified payment cannot consume points that have already been reused. It uses `profiles`, `orders`, `order_items`, `products`, and `reviews`, and all privileged point operations run through server endpoints using `SUPABASE_SERVICE_ROLE_KEY`. Apply both migrations before enabling member rewards or configuring missions in Admin. **Admin → Bar Club Engine** controls point earning/redemption rates and reward odds for customers; changes apply to customer rewards after saving.

For accurate admin behavioral metrics on an existing database, run [`supabase/BEHAVIOR_METRICS_MIGRATION.sql`](./supabase/BEHAVIOR_METRICS_MIGRATION.sql). Until it is applied, the behavior dashboard can show legacy traffic and cart metrics, but active engagement time remains unavailable. The migration starts a clean active-time measurement baseline because earlier stored session durations could be reset or missed, and changes add-to-bag rate to distinct visitor sessions that added a product divided by distinct sessions with a page view. Daily metrics use the Africa/Nairobi calendar day. The engagement average uses only visible-session time recorded on that day and sessions with at least one active heartbeat. The admin endpoint uses the server-only Supabase service-role key.

For consented area-level location, market waitlists, and Admin → Demand Intelligence on an existing database, run [`supabase/DEMAND_INTELLIGENCE_MIGRATION.sql`](./supabase/DEMAND_INTELLIGENCE_MIGRATION.sql), then [`supabase/DEMAND_INTELLIGENCE_CONTACT_NAMES_MIGRATION.sql`](./supabase/DEMAND_INTELLIGENCE_CONTACT_NAMES_MIGRATION.sql). The storefront asks customers to share an approximate area or enter one manually; declining does not block shopping. Browser coordinates are rounded before area matching and are not stored in the new location tables. Joining an uncovered area's waitlist requires a separate contact-consent checkbox. The migrations create private, service-role-only location and waitlist tables and the aggregate RPC used by the authorized admin endpoint. The contact-names migration lets authorized admins open an area row to view only launch-list contacts who consented to contact. Set `SUPABASE_SERVICE_ROLE_KEY` only in the server environment. Apply these migrations after the core setup script, then refresh Admin → Demand Intelligence.

Members can install the `/widget` dashboard as a phone home-screen app shortcut to see the launch countdown, direct and downstream referral counts, earned/available tokens and request souvenirs. Only the age band of a completed waitlist signup is stored, not date of birth; the Admin dashboard shows aggregate counts per band. Self-reported age is not legal age verification at purchase or delivery. The site records the area (not exact coordinates), GPS-match indicator/accuracy, contact channel consent, age-confirmation timestamp, product interests, order frequency and campaign/referral attribution. An optional `WAITLIST_LAUNCH_AREAS` setting or the shared `settings.logistics.dispatch_zones` controls area availability labels; without configured coverage, the site and dashboard report it as unknown. Keep Supabase, PayHero, Paystack, email, and WhatsApp secrets server-only.

For the merchant application and verification pipeline, run [`supabase/MERCHANT_OPERATIONS_MIGRATION.sql`](./supabase/MERCHANT_OPERATIONS_MIGRATION.sql) after the core setup script, then run [`supabase/DISPATCH_MIGRATION.sql`](./supabase/DISPATCH_MIGRATION.sql). Together they create the merchant application and append-only review history, permanent merchant IDs on approval, private document storage, inventory batches/movements, order traces, fulfilment/incident events, batch holds, and payment-confirmed dispatch support. Merchant applicants use `/merchant/onboarding`; authorized admins review applications and configure the document checklist by business type and county in Admin → Merchant Onboarding. Admin → Traceability & Incidents can receive lots, link batches to order items, record fulfilment/incident events, and hold inventory. Approved partners set their weekly opening times and online/offline status in Partner Workspace → Business profile; schedule times use Africa/Nairobi (EAT), include overnight shifts, and closed/offline partners are excluded from new stock allocation. After matching server-verified Paystack payment, available in-radius stock is allocated across open, accepting approved businesses, with earlier-expiry batches preferred within the same distance. If there is not enough eligible stock, the paid order stays visible in the admin Dispatch queue; “Retry available shops” safely returns unaccepted allocations from offline/closed or explicitly rejecting partners to their stock ledger and retries against businesses currently open and accepting. Rejected partners are excluded from that order's future allocations, returned trace quantities are kept out of active allocation totals, and existing accepted assignments are not silently moved. Missing customer/vendor coordinates, delivery radius, payment proof, compliance, or sufficient inventory leaves fulfillment unallocated for explicit admin review. Products without merchant-tracked batches retain the existing checkout inventory behavior. Uploaded documents are private and are delivered to reviewers only through short-lived signed URLs. Applications do not collect payout account details or become active automatically. The new operational tables are service-role-only; do not add anonymous or general authenticated access policies.

Approved Apex Market partners use `/merchant/network` to view application decisions, compliance documents, linked inventory and assigned traced orders, set their weekly opening hours and temporary online/offline state, record receipts for products already linked to their business, update permitted fulfillment stages, and submit operational incident reports. Access requires a Supabase account with a verified email matching the application email; the server rechecks ownership and approval status for every write. The Partner Workspace is the canonical Apex Market partner surface; legacy seller routes remain compatibility bridges to the same approved application and account flow. It does not create catalog products, change prices, or report payments, settlements, or revenue.

For the payment-confirmed dispatch queue on an existing database, run [`supabase/MERCHANT_OPERATIONS_MIGRATION.sql`](./supabase/MERCHANT_OPERATIONS_MIGRATION.sql) first if merchant traceability is not installed, then run [`supabase/DISPATCH_MIGRATION.sql`](./supabase/DISPATCH_MIGRATION.sql). Dispatch writes go through an authenticated admin API and a service-role-only atomic database function; the browser cannot assign riders directly. An order must be `Paid`, have a verified timestamp, and have a matching server-recorded Paystack reference/amount before merchant stock or a rider can be assigned. Cash on Delivery and manual orders stay unassigned; no COD confirmation flow is implemented. Paystack checkout callback verification records provider confirmation, while the signed webhook marks the order paid. Set `PAYSTACK_SECRET_KEY` and `SUPABASE_SERVICE_ROLE_KEY` only on the server; `RIDER_SESSION_SECRET` is recommended, but delivery tracking can sign its short-lived customer sessions with the server-only service-role key when it is unset. Configure the Paystack webhook URL as `/api/paystack/webhook`.

If you need one paste for the Dispatch connection on an existing project, use [`supabase/DISPATCH_CONNECTION_ALL_IN_ONE.sql`](./supabase/DISPATCH_CONNECTION_ALL_IN_ONE.sql) in Supabase SQL Editor. It combines merchant operations, dispatch, and Admin Dashboard Recovery in dependency order, and checks that the core schema exists first. Do not use it on a blank project; install `FINAL_ESTABLISHMENT_SQL.sql` on a new project first. The dispatch page also requires `SUPABASE_SERVICE_ROLE_KEY` in the hosting provider's private server environment (for example, Render → Environment) and a redeploy after changing environment variables; SQL cannot configure that secret. `PAYSTACK_SECRET_KEY` and `RIDER_SESSION_SECRET` are additionally needed for payment verification and rider sessions.

Admin → Runner Dispatch shows only eligible Paystack orders, vendor-fit reasons, OSRM road-distance/time rider recommendations, and recent decisions. Dispatch recommendations require a reachable OSRM service and fresh verified rider GPS (no older than five minutes); road durations are estimates and do not include live traffic. This release recommends assignments but does not silently dispatch in the background: an admin reviews the checks and explicitly confirms each recommended assignment. Rider overrides require a reason and record the admin identity, time, rider, vendor-trace IDs, and evaluated criteria; changing the rider never bypasses verified vendor fulfillment. Overrides do not bypass confirmed payment, rider verification, a recent online heartbeat, or rider load limits. Vendor checks use order-item batch traces, merchant approval/acceptance, expiry/holds, saved order price versus the current product catalogue price, and merchant radius/delivery coordinates. Supplier-specific selling prices and reliability/response scores are not stored by the current merchant schema, so the app cannot accurately score those yet. Merchant coordinates/radius must be populated for distance checks. Riders sign in with their approved phone/PIN, go online in the rider app, and grant browser location permission; the signed server session submits GPS updates to `rider_status` every 30 seconds while online.isites are shown explicitly; an admin must first resolve merchant stock/acceptance issues in Traceability & Incidents, not override them via rider assignment.

For the rider delivery lifecycle and missing Buzz map schema, run [`supabase/DELIVERY_ENGINE_AND_BUZZ_MIGRATION.sql`](./supabase/DELIVERY_ENGINE_AND_BUZZ_MIGRATION.sql) after `FINAL_ESTABLISHMENT_SQL.sql`, `MERCHANT_OPERATIONS_MIGRATION.sql`, and `DISPATCH_MIGRATION.sql`. It adds delivery milestone timestamps/event history, route-estimate history, customer delivery detail fields, and the venue/category/coordinate/media/update schema expected by Buzz screens. OSRM road routing requires a separately hosted routing backend and the server-only `OSRM_BASE_URL`; follow [`DELIVERY_ROUTING_SETUP.md`](./DELIVERY_ROUTING_SETUP.md). OSRM durations are not live-traffic-aware.

Customer delivery tracking is available at `/track`. Customers must verify with their order number and the phone used at checkout; lookups are rate-limited, and a short-lived signed session is used for refreshes. The browser receives only the fields needed to show order status and a coarse rider location (rounded to approximately 100 metres) while the order is out for delivery; the rider's private phone number and raw order row are never exposed. The tracking rate limit uses `allow_rider_login_attempt` from `SECURITY_HARDENING_MIGRATION.sql`, and signing requires the same server-only `RIDER_SESSION_SECRET` used by rider sessions. Rider GPS must be enabled and fresh for a location to appear. ETA remains unavailable unless route estimates are supplied by a configured routing integration; straight-line dispatch distance is not a road ETA.

Authorized order managers can use Admin → Support View to open the actual customer `/track` page and rider `/rider/dashboard` for an order inside the admin workspace; these are the real role screens, not separately recreated mockups. Customer preview uses a short-lived tracking session issued only after checking the admin session and order-manager permission. Rider preview reads through the admin-only support API, skips rider login and saved rider credentials, and disables all interactions, GPS updates, alerts, and rider actions. `/track` and `/rider/dashboard` allow same-origin framing for these previews; all other routes retain the `X-Frame-Options: DENY` policy. Merchant tabs remain read-only support summaries and do not impersonate merchant accounts. The view uses the server-only `SUPABASE_SERVICE_ROLE_KEY`; apply the merchant operations, dispatch, delivery-engine, order-flow, and rider doorstep-payment migrations to see all available allocation, timeline, address, and payment details. Missing optional migration data is shown as a diagnostic in the support view.

### Delivery coverage and customer location

- In **Admin → Settings → Operations**, draw and save named free-delivery areas. Each boundary needs at least three points.
- Checkout asks for device location only after the customer chooses to use it. Customers can set the pin manually instead; coverage is determined from the saved area boundaries.
- Customer-demand clusters in Admin use approximate, rounded pins from paid and delivered orders; they are not live visitor tracking.

### Souvenir image uploads

Run [`supabase/FOOD_ADDONS_MIGRATION.sql`](./supabase/FOOD_ADDONS_MIGRATION.sql) to create the public `onlinebar-assets` image bucket with an 8 MB upload limit. Allow public image reads and restrict uploads/deletes to authenticated admins using your existing admin storage policies. Do not enable unrestricted anonymous uploads. Keep any pre-existing image bucket in place so product records that still reference its public URLs continue to load.

### Campaigns and marketing data

Campaigns are stored as drafts and are not sent to external platforms. Delivery, open-rate, attribution, and A/B experiment figures remain unavailable until a publishing provider and the corresponding tracking are connected. Audience reach is calculated from customer profiles and paid/delivered orders.

### Paystack Checkout

Set `NEXT_PUBLIC_PAYSTACK_PUBLIC_KEY` to your Paystack public key in the deployment environment. Online checkout requires the customer to provide a valid email address; the app no longer substitutes a demo email or an embedded payment key. Cash on Delivery does not require an email address. Payment-confirmed dispatch also requires the server-side `PAYSTACK_SECRET_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, and the dispatch migration described above.

## 🛡️ Identity & Access Recovery

If you are experiencing the `AuthRetryableFetchError` or "Identity already exists" issues:

1. **Verify your environment**: Confirm the Supabase project URL and either the publishable key (`sb_publishable_...`) or legacy anon JWT are set correctly. A Supabase publishable key is not a Stripe key.
2. **Reset Auth Cache**: If you see "Identity already exists", use the **Switch to Vault Login** button I've integrated into the Auth Form.
3. **Identity Stitching**: The system now automatically links your anonymous browsing session to your profile upon login.
