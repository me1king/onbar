# ONLINE BAR Ticketing

The Ticketing control centre is an isolated Online Bar Admin module at `/lord/ticketing`. It uses the existing admin session for platform-owner/admin authorization and stores its records in dedicated `ticketing_*` Supabase tables. It does not read from or write to the drink-order, product inventory, merchant payout, or waitlist tables.

## Current phase

- Admin can create private event drafts and ticket tiers with KES prices, capacity, purchase limits, sale windows, venue, dates, age limit, description, and cancellation policy.
- Admins can manage each event's full venue address, precise Google Maps coordinates, entrance instructions, parking details, and public-transport guidance from the event card. Coordinate pins power guest map-search, driving/walking directions, and transit links. A pin can be entered from Google Maps or captured from the current device location; verify device coordinates point to the venue before saving.
- The Online Bar Admin Ticketing module includes a native Wave I/II/III manager. Configure waves separately for General Admission, VIP, Group Package, or Backstage / Exclusive; set each wave's price, allocation, benefits, theme, sales dates, and scheduled, previous-wave-sold-out/deadline, or owner-controlled manual activation.
- Public event pages display wave labels, benefits, current release state, remaining inventory, and an enabled purchase form for open ticket types. Inventory is reserved transactionally and prices/fees are recalculated in the database, never trusted from the browser.
- The public event listing, event details, checkout form, ticket wallet, scanner, and all Admin Ticketing workspaces share the published color mode: Midnight black, Official white, Royal violet, or Emerald. Publishing a mode updates open ticketing pages on their next refresh (or within one minute); it does not recolor the rest of the Online Bar storefront or admin panel.
- The public event listing supports typo-tolerant search across event, venue and city names; city, date and maximum-price filters; price/date sorting; device-local nearby sorting; and a map view for events with published venue coordinates. Location is requested only after the guest selects **Near me** and is not persisted.
- Ticket checkout collects the buyer's WhatsApp number and explicit consent to receive a transactional ticket-wallet link. After verified payment and ticket issuance, the buyer receives both the themed email ticket/QR and an approved WhatsApp template message with a secure wallet URL. The wallet can retry either delivery if it failed.
- Admins can configure a fixed per-ticket service fee from the Online Bar Ticketing dashboard. Fee changes are locked and audited; already-created orders retain their original price snapshot.
- The public `/tickets` and `/tickets/[slug]` pages show approved-organizer events on sale. New paid ticket orders start a PayHero M-Pesa prompt; PayHero callbacks are independently verified against its transaction-status API before a matching KES amount can atomically mark an order paid and issue tickets. Existing Paystack ticket attempts remain supported for their original callbacks and checkout links.
- Ticket orders, reservations, payment attempts and refunds are held in their own `ticketing_*` tables. Ticket payment callbacks are matched against this ledger before shop-order handling; verified ticket callbacks never enter beverage order fulfillment or the beverage sales report. The dedicated `/lord/ticketing/sales` view summarizes verified ticket revenue and refunds by period/event, independently from beverage sales.
- Failed Paystack and PayHero ticket callbacks atomically mark the ticket payment attempt and order failed and release the associated reservation. Duplicate failure callbacks are idempotent, and callbacks for paid or reconciliation-required orders do not overwrite their state.
- Every issued ticket has a random credential, stores only its SHA-256 hash plus an AES-GCM encrypted copy needed for the wallet, and is rejected on duplicate check-in. The encryption key is server-only. The guest wallet is accessible with a checkout-generated bearer token held in the payment return and the same browser's session storage. After payment is confirmed, the buyer receives an email containing the event ticket stub and each ticket's own inline QR; the wallet also lets the buyer retry delivery using its bearer token if email sending failed. Both use the currently published Ticketing theme and current event details.
- Server-side validation prevents invalid dates, price formats, purchase limits, and tier allocations beyond an event's stated capacity.
- Platform admins can create event-specific fixed or percentage promo codes, set active dates and redemption limits, and pause or reactivate them. Guests can preview the discount and revised total during checkout. The database locks a promotion while reserving a redemption, discounts only the ticket subtotal (not service fees), converts reserved uses on verified payment, and releases them after payment failure or reservation expiry.
- The core migration establishes isolated records for organizers, events, ticket tiers, reservations, orders, payment attempts and webhook deduplication, individual tickets, gate check-ins, refunds, promotions, notification jobs, and audit history.
- The reservation and gate-check-in database functions are transactional and use ticket-level locking to prevent overselling and duplicate admission.
- Gate staff use the isolated `/scanner` workspace. Platform admins assign verified Supabase Auth accounts to a specific event and gate in `/lord/ticketing/staff`; assignment and revocation are atomic and recorded in the Ticketing audit log. The scanner requires a network connection, hashes QR credentials in the browser, and the database verifies staff assignment before each atomic check-in. Scanner name, device ID and QR/manual method are recorded with each scan; the ID is descriptive only and is not an authorization credential. Gate staff can review their 30 most recent scans, and a database lock enforces a per-staff, per-event limit of 120 scans per minute.
- The Halloween-themed Trust & Security Centre records manually reported security cases, owner-only case assignment/status changes, and append-only case activity in the dedicated security migration.
- The Halloween Live Operations page reads committed Ticketing database activity and current record counts through admin-only APIs. Its database trigger journal excludes buyer contact information, payment payloads and credential hashes; the page polls every five seconds and recovers from a cursor, but is not a push/WebSocket feed.
- The live operations journal is not a substitute for protected external security logging or automated attack detection. Privileged MFA enforcement, customer accounts, five-minute QR rotation, and backup verification remain unimplemented.
- Checkout and scanner code require all documented Supabase migrations, server-side PayHero, Paystack (for existing ticket attempts and non-ticket checkout), and Resend configuration, the credential encryption key, verified staff accounts/assignments, HTTPS, and an end-to-end controlled production test before production admissions. Refund processing, transfers, transactional notification retries beyond payment-webhook/email-wallet retries, broader API abuse monitoring, and manual admission overrides are not implemented.
- The Android application currently wraps the Online Bar website. The ticket wallet is available in the website browser; there is no native ticket wallet or screenshot protection.

## Complete product scope

The isolated system is intended to grow through release-gated phases into:

1. **Event discovery and customer wallet:** the public event listing with search/filter/proximity/map discovery, event detail pages, guest order wallet, and digital QR tickets are implemented. Organizer onboarding, full media/lineup management, customer accounts, and email-based wallet recovery remain outstanding.
2. **Ticket commerce:** basic server-priced checkout, KES fee snapshots, wave-aware inventory reservations, purchase limits, capped event-scoped fixed/percentage promo codes, PayHero M-Pesa payments, complimentary tickets, and atomic issuance are implemented. Referral attribution and a scheduled reservation-expiry worker remain outstanding.
3. **Verified payments and finance:** PayHero ticket callbacks are transaction-verified server-side, with amount/reference matching and idempotent ticket issuance; existing Paystack ticket attempts retain signature-checked callbacks. Direct Daraja STK Push, refunds, dispute evidence, settlement, and reconciliation tooling remain outstanding.
4. **Admission operations:** random per-ticket credentials with stored hashes, event/gate/staff-scoped online QR check-in, atomic duplicate rejection, refunded/revoked-ticket rejection, audited overrides, and a documented, limited offline-contingency policy.
5. **Organizer and platform administration:** organizer onboarding/approval, event moderation, event-scoped staff, role/permission controls, ticket/order/support tools, sensitive-action approvals, cancellation/postponement workflows and audit history.
6. **Communications and growth:** transactional email/in-app/SMS/WhatsApp queues with templates, consent, retries and receipts; waitlist invitations kept separate from purchases; promo codes; affiliate attribution and refund-adjusted commission records.
7. **Reporting and operations:** tickets sold versus attendance, gross versus net proceeds, fees/refunds, conversion and sales pace, payment/reconciliation exceptions, failed notifications, monitoring, backup restore and privacy/retention operations.

These are product targets, not features that the current draft-only phase claims to have shipped. Each phase requires its own permission checks, failure/recovery behavior and tests before it is enabled.

## Database setup

Apply these migrations in order to the same Supabase project used by Online Bar Admin: `TICKETING_CORE_MIGRATION.sql`, `TICKETING_SERVICE_FEE_ADMIN_MIGRATION.sql`, `TICKETING_SECURITY_MIGRATION.sql`, `TICKETING_LIVE_OPERATIONS_MIGRATION.sql`, `TICKETING_WAVES_MIGRATION.sql`, `TICKETING_SCANNER_MIGRATION.sql`, `TICKETING_SCANNER_HISTORY_MIGRATION.sql`, `TICKETING_COMMERCE_MIGRATION.sql`, `TICKETING_PAYMENT_CURRENCY_FIX_MIGRATION.sql`, `TICKETING_SALES_REPORT_MIGRATION.sql`, `TICKETING_EVENT_PUBLISHING_MIGRATION.sql`, `TICKETING_VENUE_LOCATION_MIGRATION.sql`, `TICKETING_EMAIL_DELIVERY_MIGRATION.sql`, `TICKETING_WHATSAPP_DELIVERY_MIGRATION.sql`, `PAYHERO_TICKETING_MIGRATION.sql`, and finally `TICKETING_PROMOTIONS_MIGRATION.sql`. The commerce migration enables atomic KES checkout, wallet access, verified payment recording, and ticket issuance. The payment-currency fix ensures the KES-only payment attempt table supports the checkout RPC's inserts on projects that already applied the original commerce migration. The sales-report migration adds the admin-only isolated ticket ledger and transactional failed-payment/reservation handling. The PayHero migration routes new paid ticket checkouts to PayHero, preserves existing Paystack attempts, and adds server-only reference/confirmation RPCs. The promotions migration adds service-role-only redemption reservations and the server-priced promo checkout function; it routes new paid promo-enabled checkouts through PayHero and must be applied after the PayHero migration. The scanner migration audits staff assignment changes and verifies event-scoped access at each scan; the scanner-history migration adds scan metadata/history and serialized rate limiting. The event-publishing migration adds the owner-only publish/pause action used in the OnBar admin and checks the event, organizer, venue and available ticket wave before making a listing public. The venue-location migration adds the editable map pin and guest arrival-guide fields. The email-delivery migration creates a service-role-only email delivery ledger. The WhatsApp-delivery migration adds buyer phone and encrypted wallet-link storage plus a private delivery ledger with lease-based retry handling; successfully delivered links have their encrypted token copy removed. All ticketing tables are private to the server-side `service_role`; the browser never receives database credentials or raw stored ticket credentials.

In OnBar Admin, open Ticketing to create a draft, add an active ticket wave and confirmed venue/event details, then use **Open event for public sales** on that event card. Only the platform owner sees this action. The database rejects publication unless the event is in the future, its organizer is approved, venue details are present, and at least one active ticket option is currently available. Use **Pause public sales** to remove a live event from discovery; already-paid tickets remain valid. No event is created or published automatically.

Keep `SUPABASE_SERVICE_ROLE_KEY`, `PAYHERO_AUTH_TOKEN`, `PAYHERO_CHANNEL_ID`, `PAYSTACK_SECRET_KEY`, and `TICKETING_CREDENTIAL_ENCRYPTION_KEY` server-only. Set `PAYHERO_AUTH_TOKEN` to the PayHero Basic Auth token from the PayHero developer account and `PAYHERO_CHANNEL_ID` to the M-Pesa channel ID; see [PayHero's official API documentation](https://docs.payhero.co.ke/). PayHero accepts whole-KES M-Pesa amounts, so each ticket price plus its service fee must total a whole shilling. Do not paste payment credentials into chat or browser-visible settings. If credentials were exposed, revoke and rotate them before deployment. PayHero callbacks are received at `/api/payhero/ticketing/webhook` with a unique per-payment callback key; the server verifies the key and rechecks transaction status against PayHero before issuing tickets. Keep the existing Paystack webhook at `/api/paystack/webhook` for regular shop payments and historical Paystack ticket attempts. Generate the ticket encryption key with `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` and store it as an environment variable in both local development and the production host. Do not change or lose this key after tickets have been issued; existing wallet credentials cannot be decrypted with a different key. Configure `NEXT_PUBLIC_BASE_URL` to the public HTTPS site origin. The return link is a bearer credential and must not be shared.

## Remaining release gates

1. Apply and verify every migration in the listed order; set PayHero channel/authentication, Paystack keys for non-ticket payments, and the encryption key in the hosting environment; configure the HTTPS PayHero callback and verify provider delivery.
2. Run a controlled PayHero test purchase and test valid payment, failed/duplicate/delayed callback, amount mismatch, reservation expiry, complimentary ticket, and credential decryption.
3. Provision verified staff accounts, assign event-scoped gate roles in `/lord/ticketing/staff`, and scan a paid ticket at the event; verify the second scan is rejected. Test unpaid, wrong-event, refunded/revoked, and closed-event results.
4. Configure `RESEND_API_KEY`, a verified `RESEND_FROM_EMAIL`, `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_ID`, and an approved Meta WhatsApp message template named by `WHATSAPP_TICKET_TEMPLATE_NAME` with language `WHATSAPP_TICKET_TEMPLATE_LANGUAGE`. Its body must contain three text placeholders in order: event title, order reference, and wallet URL. Test payment-to-email/WhatsApp delivery and wallet retry before relying on production tickets. The email contains issued QR credentials and the WhatsApp message contains a bearer wallet link; treat both as private and do not forward them. Cross-device wallet recovery is not available if both are lost. Complete refunds, settlements, payment reconciliation, broader API abuse monitoring, accessibility/privacy review, backup recovery, and concurrency/authorization testing. The scanner enforces a per-staff/per-event limit of 120 scans per minute in the database.
5. Run a controlled pilot with staff and support available. Do not treat the feature as production-ready until these external setup and end-to-end checks pass.

Money is stored as integer minor units with an explicit ISO currency. A checkout redirect, screenshot, or client-side status must never be treated as proof of payment.
